# Local-first invoice extraction with an evaluation harness

Extract structured data (vendor, invoice number, date, currency, subtotal, tax, total) from English and French invoices, **fully offline on a CPU-only laptop**, and measure how well it works.

> **Status: MVP in progress.** The parsing pipeline, rule-based baseline, validators and evaluation harness are done. The local-LLM extractor works but has **not yet been evaluated on a held-out dataset**, so no LLM accuracy claim is made here. See [Status and roadmap](#status-and-roadmap).

## Why this project

Finance and accounting teams still re-type invoice data by hand. Cloud extraction APIs cost money per page and require sending financial documents to a third party. This project explores the other path: local OCR and a small local LLM, plus deterministic validation, with an evaluation harness that reports honest numbers.

The point of the project is **measurement and trust**, not just extraction: which approach is more accurate, what does it cost in time, and which documents should a human review?

## How it works

```
PDF / image
   │
   ├─ PDF has a text layer? ── yes ──► native text extraction (PyMuPDF, line-aware)
   │                           no
   └──────────────────────────────────► OCR (Tesseract, English + French)
                                              │
                                              ▼
                            extractor (regex baseline  or  local LLM via Ollama)
                                              │
                                              ▼
                      validators: arithmetic, dates, currency, missing fields
                                              │
                              ┌───────────────┴───────────────┐
                        all checks pass                  a check failed
                        (auto-accept)                  (flag for human review)
```

Key design decisions:

- **Native text first, OCR only as fallback.** Native extraction is exact and about 20× faster.
- **Schema-constrained LLM output.** The model is forced to return JSON matching a Pydantic schema. This guarantees structure, not correct values, so values are still validated afterwards.
- **Abstention is preferred over guessing.** Every field is nullable. A missing field is routed to review, while a confident wrong value is the expensive error.
- **Arithmetic validation and repair.** If exactly one of subtotal / tax / total is missing, it is derived from the other two. If the numbers don't add up, the document is flagged.
- **Cached OCR and LLM calls**, so evaluation runs are fast and reproducible.

## Dataset

Documents are **synthetic**, generated by `scripts/generate_data.py` with a fixed seed: 120 invoices, balanced across English/French and native PDF/scan. Scans are rasterized, slightly rotated, blurred and noised, and have no text layer, which forces OCR. Labels come from the generator, so ground truth is exact.

**Limitation:** synthetic documents are cleaner and more uniform than real invoices, and the baseline was written by the same person as the generator, so it knows the label wording. Results below are on this **development set** and should not be read as real-world accuracy.

## Results so far

### Regex baseline (120 synthetic documents, development set)

| Extractor | Fields F1 (micro) | All fields correct | Scans: all fields correct | Silent errors* |
|---|---|---|---|---|
| Baseline | 99.5% | 94.2% | 88.3% | 2 |
| Baseline + arithmetic repair | 99.8% | 98.3% | 96.7% | 2 |

\*A silent error is a document that passed every validation check but contains a wrong value. Both are OCR corruptions of non-numeric fields (a vendor name and a currency symbol), which arithmetic checks cannot catch.

The repair step was designed after inspecting 3 dev-set errors, so its gain is in-sample.

Timing on an Intel Core i5-8265U (CPU only, 8 GB RAM): about 0.08 s per native PDF and about 1.5 s per scanned page (OCR), measured over 60 documents each.

### LLM prompt iteration (qwen2.5:1.5b via Ollama, 6 development documents, 42 fields)

| Prompt | Correct | Wrong | Left blank |
|---|---|---|---|
| v1: short instructions | 18 | 2 | 22 |
| v2: explicit field definitions | 31 | 2 | 9 |
| v3: v2 plus one worked example | 39 | 1 | 2 |

The prompt was tuned on these same 6 documents, so the numbers are optimistic. One of the two remaining failures is instructive: OCR produced a garbled amount and the model returned a plausible number that appears nowhere in the text. The arithmetic validator flags such documents for review.

LLM inference took roughly 8 to 20 s per document on this CPU (it varies with machine load), compared with about 1 ms for the baseline.

## Quickstart (Windows)

Requirements: Python 3.10+, [Tesseract](https://github.com/UB-Mannheim/tesseract/wiki), [Ollama](https://ollama.com).

```bat
git clone https://github.com/asma19-98/doc-extraction.git
cd doc-extraction
python -m venv .venv
.venv\Scripts\activate.bat
pip install -r requirements.txt

:: French OCR data, kept inside the project
mkdir tessdata
copy "C:\Program Files\Tesseract-OCR\tessdata\eng.traineddata" tessdata\
copy "C:\Program Files\Tesseract-OCR\tessdata\osd.traineddata" tessdata\
curl -L -o tessdata\fra.traineddata https://github.com/tesseract-ocr/tessdata_fast/raw/main/fra.traineddata

:: Local model (only needed for the LLM extractor)
ollama pull qwen2.5:1.5b
```

If Tesseract is installed elsewhere, set the `TESSERACT_CMD` environment variable to its path.

```bat
:: 1. generate the synthetic dataset
python scripts\generate_data.py --n 120

:: 2. parse every document once (OCR results are cached)
python -m scripts.build_text

:: 3. evaluate
python -m scripts.evaluate --extractor baseline
python -m scripts.evaluate --extractor baseline_repaired
python -m scripts.evaluate --extractor llm_repaired --limit 20   :: slow: roughly 10-20 s per document

:: tests
python -m pytest -q
```

Each evaluation prints a results table and saves it to `results/`.

## Project structure

```
docextract/     parsing, normalization, baseline, LLM extractor, validators, metrics
scripts/        data generation, text caching, evaluation
tests/          unit tests
results/        saved evaluation reports
```

## Limitations

- Synthetic data only so far; real-world accuracy is unknown.
- One document family (single-page invoices), English and French, with no line-item extraction.
- The LLM extractor has not been evaluated on a held-out set, and a 1.5B model on CPU is slow.
- Numeric dates are read as day/month/year; ambiguous formats are not handled yet.
- Arabic, handwriting and complex layouts are out of scope.
